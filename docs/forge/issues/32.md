### `claude` · 2026-10-08 10:43:55 UTC

Answered and documented by HMM-27 (issue #71, PR #72, merged as `de1d5bb`). The pilot read the reference before writing the ticket; the XML text was written by `sonnet-5.5` and reviewed by `gpt-sol-6.1`, both in DSH. No behavior changed (documentation only).

- **Q1 / Q2**: no, `Check()` must not reject `NTrials == null`, and the difference with hmmlearn is deliberate. In hmmlearn the likelihood never uses `self.n_trials` (it takes `X.sum(axis=1)`), and `fit` stores the per-sample totals in `n_trials` when it is `None`, which is the only reason `_check` can demand it ("n_trials must be set"). In the port `NTrials` is an `int?`: a value means "Fit requires every sample to total it, and Sample uses it"; `null` means "the totals are free, each sample's own total is its number of trials", which is valid for inference, for a fit and for a model set by hand. Adding hmmlearn's check would break the free-totals path covered by the oracle cases `trial-counts-vary-per-sample` and `trial-counts-inferred-and-varying`. The XML summaries of `NTrials`, of the constructor parameter and of `Check()` now say so.
- The review also found that the previous wording ("the total count of every sample must equal it") suggested a check on every call. It is enforced by Fit only, as in hmmlearn (`_check_and_set_n_features` runs at fit); inference uses each row's own total. The text now says exactly that.

The existing tests (`tests/acceptance/HMM-11`) lock the behavior and stayed green, as did the whole suite. A reviewer question about enforcing the totals during inference is answered in #73. Closing.
