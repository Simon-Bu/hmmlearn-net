# HMM-28 — AbstractHmm - inference rejects an observation matrix with a wrong number of columns

> Forgejo issue #74 · closed · opened 2026-10-08 10:43:45 UTC by `claude` · closed 2026-10-08 10:51:12 UTC  
> Labels: `state/merged` · Milestone: J5

**Spec (authoritative):** [`.factory/tickets/HMM-28.yml`](https://github.com/Simon-Bu/hmmlearn-net/blob/main/.factory/tickets/HMM-28.yml)

**Objective.** Fix the gap that the review of HMM-15 left open (follow-up issue #43) at its root, as that review recommended: a base-level check called by
the inference entry points of AbstractHmm. Today Score, ScoreSamples, Decode, Predict and PredictProba never compare the number of columns of x
with what the model expects. The pilot ran each case on the merged code:
- PoissonHmm (3 features): x with 2 columns returns a wrong score silently, x with 4 columns throws IndexOutOfRangeException;
- MultinomialHmm (3 features): x with 2 columns returns a wrong score silently, x with 4 columns throws IndexOutOfRangeException;
- CategoricalHmm (one symbol per sample): x with 2 columns ignores the second column silently.
hmmlearn raises a ValueError (numpy shape error) for such input; the port must throw the documented ArgumentException, whatever the model.
Gaussian models already do (Stats checks the shapes); the guard makes the rule uniform and explicit.
The coder writes the tests of this ticket and then the fix (no separate tests agent).

**Criteria**

- **C1** — For PoissonHmm, MultinomialHmm, CategoricalHmm, GaussianHmm and GmmHmm (and the variational models when included), x with a wrong number
of columns (one too few, one too many; for CategoricalHmm 2 columns) throws ArgumentException (exact type) from Score, ScoreSamples,
Decode, Predict and PredictProba, and x with the right number of columns still gives a finite score.
 · `dotnet run --project tests/HmmLearn.Tests -- --filter-class HmmLearn.Tests.Acceptance.Hmm28.ColumnCountTests`

- **C2** — The check lives in AbstractHmm (one virtual member and one call in each entry point), the categorical models override it with 1, valid
input is unaffected (the whole suite stays green) and the new tests are meaningful: at least one fails on the unfixed code and passes on
the fix (the reviewer checks this against the diff and the coder's summary); no test re-implements the code under test.
 · judged by the reviewer

- **C3** — The XML summaries of Score, ScoreSamples and Decode state the rule; the code stays readable: short methods, no dead code. · judged by the reviewer

**Roles.** coder: `sonnet-5.5` · reviewer: `gpt-sol-6.1` · 2 rounds at most

**Writable scope.** `src/HmmLearn/AbstractHmm.cs`, `src/HmmLearn/CategoricalHmm.cs`, `src/HmmLearn/VariationalCategoricalHmm.cs`, `tests/acceptance/HMM-28/**`

_Published by the pilot. The ticket's state is carried by the `state/…` labels, updated by the orchestrator._
