**Review remarks left open**
- [ ] **R1** (minor) `src/HmmLearn/BaseHmm.cs:138` — For a transition matrix whose stationary distribution is NOT unique - e.g. the identity matrix, or two absorbing states - the system (P^T - I) with the normalization row is still rank-deficient, and MathNet's LU().Solve then returns NaN entries instead of throwing: I probed MathNet 5.0.0 (net48 build) in memory, solving [[0,0],[1,1]] (exactly the system built from the 2x2 identity transmat) against [0,1], and it returned [NaN, NaN]. GetStationaryDistribution would therefore return an all-NaN vector that does not sum to 1, while the reference linalg.eig returns an eigenvector of the eigenspace (e.g. [1, 0, ..., 0] for the identity). None of the four golden stationary cases hit this (they all have a unique stationary distribution), and no criterion pins it, so this is a minor gap, not a criterion violation; it also means the XML summary's 'normalized to sum 1' does not hold on those inputs. Expected: Either fall back to the eigendecomposition of the transposed matrix (as in the reference) when the linear system is singular/NaN, or explicitly state in the XML summary that the transition matrix must have a unique stationary distribution. No test change is required; the locked acceptance tests are sufficient for the ticket's criteria.

Fixed by HMM-26 (issue #68, PR #69, merged as `83dc18a`). The tests and the fix were written by `sonnet-5.5` (tests first, red on the unfixed code) and the review was done by `gpt-sol-6.1`, both in DSH.

The first option of the issue was taken (a valid distribution instead of NaN), with a deterministic rule instead of an eigendecomposition: when the transition matrix has several closed classes, `GetStationaryDistribution` returns the stationary distribution of the closed class that holds the lowest state index, and 0 elsewhere. A unique distribution is computed exactly as before (same full-size solve). The rule agrees with hmmlearn 0.3.3 on four new oracle cases, computed by hmmlearn itself and added to `oracle/golden/stationary.json` (`non_unique_cases`: identity, two absorbing states and a transient state, two disconnected 2-cycles, two ergodic blocks); the four existing cases are unchanged. In general hmmlearn returns whichever eigenvector LAPACK finds first, which is not specified; the port is deterministic and says so in its XML summary.

Tests: `tests/acceptance/HMM-26/NonUniqueStationaryTests.cs`; the whole suite stayed green in the orchestrator verification. Q1 of this issue (same message for a null and a wrong-length `StartProb`) is covered by the existing HMM-9 tests, which keep one exact message for both cases; no change. Closing.
