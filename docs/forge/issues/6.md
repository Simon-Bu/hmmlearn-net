**Review remarks left open**
- [ ] **R1** (minor) `src/HmmLearn/InternalUtils.cs:75` — The length sum is accumulated in an unchecked int (total += lengths[i]), so a sum that wraps around 2^31 can coincidentally equal the row count and bypass the documented sum check. Concrete instance: lengths [1073741824, 1073741824, 1073741824, 1073741824] (true sum 2^32) on a 0-row matrix wraps to 0, passes 'total != nRows', and the method then throws an undocumented OverflowException (array beyond 2^31 elements), IndexOutOfRangeException or OutOfMemoryException. The documented contract (and the Python reference, whose numpy int64 cumsum does not wrap) requires ArgumentException there because 2^32 != 0 rows. No test or golden case covers this; treated as a minor ambiguity left open by the criteria (ticket constraint 6: choose the most reasonable reading, note the assumption). Expected: Accumulate the sum in a long (a sum of int elements is < 2^62, so it cannot overflow) and compare it to nRows, so the documented sum-mismatch ArgumentException fires for every input. The rest of the method is already correct.

**Unanswered questions**
- [ ] **Q3** (reviewer, qwen-q4-long, its Q1) — ValidateCovars on a zero-feature covariance (tied shape (1,0,0), full shape (nc,0,0)) passes the shape checks and calls MathNet's Matrix<double>.Build.Dense(0,0).Evd(Symmetricity.Symmetric). The hmmlearn reference accepts such shapes (scipy eigvalsh on a 0x0 matrix returns an empty array, so no ValueError). I could not empirically verify MathNet 5.0.0's behaviour on a 0x0 symmetric Evd in the review sandbox (pwsh 5.1 cannot load net9.0 assemblies, probe files are not permitted, and the dotnet-fsi stdin path is broken by a phantom BOM). If MathNet throws there, ValidateCovars would throw an undocumented exception on a shape the reference accepts; if it returns an empty eigenvalue list, the current code already matches the reference. How should this degenerate case be handled? Options: Add a guard 'if (n == 0) return;' at the top of CheckMatrix: a 0x0 matrix is vacuously symmetric and positive definite, exactly matching the Python reference, and it removes any doubt about MathNet's 0x0 handling. / Leave CheckMatrix as is, after verifying (with a quick probe outside the review sandbox) that MathNet 5.0.0's 0x0 symmetric Evd returns an empty eigenvalue list rather than throwing.. Recommendation: Prefer the explicit n == 0 guard: one line, matches the reference semantics, and keeps the 'only documented exceptions' constraint watertight; it only becomes dead code if the 0x0 behaviour of MathNet 5.0.0 is verified to be fine.
