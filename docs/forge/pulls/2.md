| C1 | satisfied | Normalize divides in place by the sum on all four paths (vector; matrix axis 0 per column, axis 1 per row, null whole) with the zero-sum guard (sum == 0 -> 1, zeros stay zeros, no NaN) on every path, including axis 0 and axis null where the Python reference does not guard (documented port deviation, oracle/README.md). The bad-axis guard (axis < 0 or > 1) throws ArgumentOutOfRangeException before any element is modified. All five normalize_cases were independently re-derived from the golden file and match (maxdiff <= 2.8e-17), and the golden-loop test reproduces every case in place; the hand-checked tests additionally cover in-place vector normalisation, zero sums on both axes and the whole matrix (including a cancelling non-zero row), and bad axes -1/2/5 asserting the exact exception type and an untouched array. Orchestrator verify run (NormalizeTests filter) is green. |
| C2 | satisfied | LogNormalize subtracts the stable log-sum-exp in place (maximum factored out; if the maximum is infinite it is the LSE itself, so +inf input gives -inf for finite entries and NaN for the +inf entries, and an all -inf row/column gives NaN). The vector overload is pure stable LSE (lone -inf -> NaN, lone finite -> 0); the length-1-axis rule (every element becomes 0, even -infinity) applies to the matrix overload's chosen axes only, exactly as the interface and the pilot's decision state. All eight log_normalize_cases were independently re-derived and match, including rows-with-minus-infinity, row-of-minus-infinity-gives-nan, single-column-gives-zero (whose golden input contains -Infinity, so the 'even -infinity' clause is covered by the golden file) and single-row-gives-zero. Hand-checked tests add stability at +-1000, single-element and lone -inf vectors, +inf maximums (vector and matrix), and bad axes with exact exception type and untouched array. Orchestrator verify run (LogNormalizeTests filter) is green. |
| C3 | satisfied | FillCovars expands the four compact shapes (spherical (nc,1,1) -> variance times identity, diag (nc,1,nf) -> diagonal, full (nc,nf,nf) -> copy, tied (1,nf,nf) -> repeated) into a fresh (nc,nf,nf) tensor; the input is never written (verified by reading: all writes go to the newly allocated result) and a hand test asserts the input is byte-for-byte unchanged for the diag and full shapes. Any shape that does not match the covariance type, nComponents or nFeatures throws exactly ArgumentException (Assert.Throws, no subclass) via RequireShape; 11 mismatch cases are hand-checked with the exact type. All four fill_covars_cases were independently re-derived and match exactly (maxdiff 0). Orchestrator verify run (FillCovarsTests filter) is green. |
| C4 | satisfied | Only the five interface members are public; LogSumExp and RequireShape are private static; no global state; no dead code or leftover stubs; methods are short and linear. The csproj is unchanged, so no package was added and the implementation uses only the BCL (the MathNet.Numerics reference pre-exists in the committed skeleton and is not used here). Every public member keeps an XML summary that matches the behaviour, with one wording imprecision in the FillCovars closing sentence (see R1). |

**Remarks**
- **R1** (minor) `src/HmmLearn/Utils.cs:140` — The closing sentence of the FillCovars XML summary says 'A shape that does not match the covariance type throws ArgumentException', but the code and the ticket interface also throw when the shape does not match nComponents or nFeatures (for example a spherical (2,1,1) passed with nComponents=3). The 'Compact shapes:' line of the same summary implies the full condition, so the behaviour is correct; the sentence alone understates it. Expected: Align the sentence with the interface, e.g. 'A shape that does not match the covariance type, nComponents or nFeatures throws ArgumentException'. No behaviour change required.
- **R2** (minor) `src/HmmLearn/Utils.cs` — For negative nComponents or nFeatures (outside the documented domain - no compact shape can match a negative count) FillCovars reaches the array allocation and the runtime throws ArgumentOutOfRangeException instead of the documented ArgumentException; the interface is silent for such inputs. nComponents=0 / nFeatures=0 are allocable and arguably valid, so only the negative values are in question. Expected: Define the behaviour for negative dimensions (guard and throw the documented ArgumentException, or document the runtime exception). Up to the pilot's discretion; if considered out of scope for this ticket, close the remark without a fix.
