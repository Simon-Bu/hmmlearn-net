**Review 1** — approved
PoissonHmm and PoissonStatistics are a faithful port of hmmlearn's PoissonHMM (hmm.py 945-1075) and BasePoissonHMM (_emissions.py 372-410), checked line by line against the reference: the M-step uses the TOTAL posterior mass n = sum of all Post entries with per-state y_bar = Obs[c,f]/Post[c] (the pinned hmmlearn quirk), Init is the method-of-moments gamma (shape mean^2/variance, scale variance/mean, population variance) exactly as _init, Check matches _check (NFeatures recorded from the columns of Lambdas when unknown, documented shape message) plus the ticket's non-negative-rate rule, the log likelihood is count*log(rate) - rate - GammaLn(count+1) with 0*log(0)=0 and -infinity for a positive count under a zero rate (matching scipy's poisson.logpmf), the statistics, the accumulation (Post += column sums, Obs += posteriors^T x) and the per-feature Poisson draws (zero rate exactly 0) all agree, and GetNFitScalarsPerParam gives s=nc-1, t=nc(nc-1), l=nc*nf with null while NFeatures is unknown (the CategoricalHmm pattern, the base 'null means unknown' contract, pinned by the locked test). I reran every verify command myself: InferenceParityTests 4/4, FitParityTests 11/11 (all four fit cases, both implementations, including gamma-prior-uses-total-posterior-mass), ValidationTests 12/12, SamplingAndFitTests 9/9, full suite 743/743, all green. Constraints hold: the coder's commit (9306af7) changes only src/HmmLearn/PoissonHmm.cs, every signature of the ticket interface is kept, every public and protected member has an XML summary that matches the behaviour, no abstract member was added, no package was added, and no caller array is mutated (Lambdas is replaced by a new array in Init and DoMStep, confirmed in the code and by the locked no-mutation tests). The golden file contains exactly the cases the criteria name (inference: two-states-three-features with 3 sequences and zero-counts; fit: defaults, tight-tolerance, lambdas-only, gamma-prior-uses-total-posterior-mass), so 'every case of the oracle' is fully exercised. The locked tests also fail against the stubs with NotImplementedException by inspection (they call Score/Fit/DoMStep/GenerateSampleFromState/GetNFitScalarsPerParam, all of which threw in the stub commit). One minor remark (R1): the inference entry points do not validate the column count of x against NFeatures, a gap inherited from the merged base design and present in every sibling model, outside this ticket's writable scope. The coder's Q1 needs no answer: the locked test pins the null convention, so the behaviour is settled.

**Remarks**
- **R1** (minor) `src/HmmLearn/PoissonHmm.cs:154` — The inference entry points (Score, ScoreSamples, Decode) do not validate the column count of x against NFeatures: with a model whose NFeatures is 3, a Score/ScoreSamples/Decode call with x having 2 columns silently computes the likelihood over the 2 available features and returns a wrong result without any exception, while with 4 or more columns ComputeLogLikelihood throws an IndexOutOfRangeException (not an ArgumentException). C3's 'a different number of columns than the model has features' is therefore rejected only through Fit (base.Init -> CheckAndSetNFeatures), which is exactly what the ticket's acceptance contract and the locked test a_different_number_of_columns_than_the_model_features_throws define. Expected: This is not a defect of this ticket: Check() takes no x, CheckObservations is static, and CheckAndSetNFeatures is invoked only by base.Init, so the gap is inherited from the merged base design, exists identically in CategoricalHmm, MultinomialHmm and GaussianHmm (already accepted in earlier tickets), and cannot be fixed within the writable scope (only src/HmmLearn/PoissonHmm.cs) without deviating from every sibling model. No change is requested for HMM-15; the guard belongs to a future base-level ticket (e.g. a virtual x-shape check called by the inference entry points of AbstractHmm).
