**Review 1** — approved
Approved. The M-step in src/HmmLearn/VariationalGaussianHmm.Learning.cs is a faithful port of VariationalGaussianHMM._do_mstep (vhmm.py 697-784): base start/transition update first, then 'm' (beta = beta_prior + post, means = (beta_prior*means_prior + obs)/beta) and 'c' with per-type helpers — Full per-state, Tied summing over states, Diag, Spherical taking the mean over features — and the 'c' update reads the just-written BetaPosterior/MeansPosterior when 'm' is in Params, the stored ones otherwise. I verified every formula against the reference line by line, checked the compact shapes (nc,nf,nf / 1,nf,nf / nc,1,nf / nc,1,1), that every update allocates new arrays, that Covars is assigned through the validating property (degenerate result throws ArgumentException), and that no array is mutated in place. The coder's commit touched exactly the one writable file; no new package (the file has no usings). I reran all verify commands: FitParityTests 32/32, MStepTests 12/12, FitBehaviourTests 13/13, full suite 1225/1225 (exit 0), and confirmed the golden files contain all 4 cases per file with complete expected blocks (no skipped comparisons), so the parity tests are not vacuous; 24 of the 32 parity cases exercise the new m/c code against hmmlearn numbers over 10 and 100 iterations, both implementations. The pilot's fixes to the locked tests (Q3-Q7: Full expectation per state, stc fit with stored posterior equal to the prior) are present in the tree and the corrected expectations match the reference formulas; I confirmed them by rerunning the suite, as the pilot asked. All stated assumptions of the acceptance tests hold: stc/stm reading of C3 (Q1), the 1e-6 lower-bound slack (Q2), formula-computed MStep expectations on a consistent weighted Gaussian sample, seeded fits, and the 'st' cases passing against the stub without masking the missing work. C4 holds: one helper per covariance type, short methods, no dead code, XML summaries match the behaviour. One minor remark: the locked tests exercise only two features (oracle nc=3/nf=2, hand-made statistics nc=2/nf=2), so the spherical averaging and tied summation branches are only exercised at nf=2; the code is generic and the criteria are met as written, so this is a coverage note on locked tests, not a defect.

**Remarks**
- **R1** (minor) `tests/acceptance/HMM-22/MStepTests.cs:22` — Every locked test uses exactly two features: the oracle fit cases are nc=3/nf=2 and the hand-made M-step statistics are nc=2/nf=2. The spherical 'mean over the features' branch and the tied 'sum over the states' branch are therefore only exercised at nf=2 (and nc=2 in the hand-made cases). A future regression that only manifests with nf >= 3 (e.g. an off-by-one in the feature loop) would not be caught by these tests. Expected: No change required: the code's loops are generic in nf and nc, the criteria are met exactly as written (C1 is pinned to the oracle files, C2 to the formulas per type), and the tests are locked. Recorded for the record as a coverage observation; a later ticket could add a 3-feature hand-made M-step case.
